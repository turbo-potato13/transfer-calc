# Где живёт приложение

## Question

Опубликованный Artifact не может делать сетевые запросы вообще. Где тогда живёт страница, если автоподстановка курсов должна работать?

## Решение направления (2026-09-03)

Пользователь выбрал **Oracle Cloud** — тот же бесплатный инстанс, где уже крутится `reels-tg-bot`. Ticket остаётся открытым, пока не подтверждены факты с машины и не решён вопрос с доменом (ниже).

### Что известно о машине — снято с сервера 2026-09-03

Не предположения, а вывод команд:

| | |
|---|---|
| Шейп | `VM.Standard.E2.1.Micro` — **AMD x86_64**, 1 OCPU (2 потока), 0.48 Gbps |
| ОС | Ubuntu 22.04.5 LTS, Python 3.10.12 |
| Память | **956 Mi всего, 445 Mi доступно, в swap уже 352 Mi** |
| Диск | 45 G, занято 7.7 G (17%) — с запасом |
| Слушают порты | только 22 (sshd), 53 (systemd-resolved, локально), 111 (rpcbind) |
| Веб-сервер | **нет** — ни nginx, ни caddy, ни apache, ни docker |
| iptables | из нового пропускает только 22, заканчивается на `-j REJECT` |
| Работает | один сервис `reels-tg-bot` |

Ключевое — **память, а не процессор**. Гигабайт, из которого треть уже в swap: почти наверняка `ffmpeg` при скачивании видео выдавливает страницы. Это окончательно исключает долгоживущий backend (FastAPI/Flask/Node) и подтверждает выбор «cron + статика»: Caddy в простое ест ~20–30 МБ, Python-скрипт живёт пару секунд раз в полчаса и умирает, пиковая нагрузка нулевая.

Уточнение к README бота: там рекомендован ARM Ampere, но фактический инстанс — AMD E2.1.Micro. Баннер в консоли про изменение лимитов Ampere A1 (2 OCPU / 12 GB) к этой машине **не относится** — он про ARM-шейпы.

Из репозитория (`C:\Projects\reels-tg-bot`): пользователь `ubuntu`, проект в `/home/ubuntu/reels-tg-bot`, venv, запуск через systemd, деплой `git pull --ff-only` + `systemctl restart`, cron раз в неделю обновляет `yt-dlp`. Готовый образец того, как на этой машине принято разворачивать — новый сервис стоит сделать по тому же шаблону.

Нагрузка бота: один чат на 14 человек, 5–10 запросов в сутки, ~5% ресурсов по наблюдению пользователя.

### Рекомендуемая форма развёртывания

Моя рекомендация, ждёт возражений:

- **Без долгоживущего backend-процесса.** Скрипт на Python (он уже есть на машине) по cron или systemd-timer раз в 15–30 минут забирает три источника — Прибанк, НБМ, ПРБ — и пишет один файл `rates.json` в статическую папку вместе с временем запроса. Страница и `rates.json` раздаются веб-сервером как статика. Если скрипт упал, страница видит старый `rates.json` с его временем и говорит об этом. Кроме веб-сервера, ничего не нужно «держать живым», и ни один процесс не может утечь по памяти.
- **Веб-сервер — Caddy.** Один бинарник, автоматический TLS от Let's Encrypt при наличии домена, конфиг в три строки, ~20 МБ памяти в простое.
- **Ресурсы:** пренебрежимо мало на фоне `ffmpeg`/`yt-dlp` у бота. Python-скрипт живёт две секунды раз в полчаса.
- **Почему не живой API:** для официальных курсов, обновляемых раз в сутки, и наличных, меняющихся несколько раз в день, снимок раз в 15–30 минут неотличим от живого запроса, а хрупкости на порядок меньше.

### Домен и HTTPS — решено

Своего домена у пользователя нет (2026-09-03). HTTPS при этом стал **обязательным**, а не желательным: после уточнения в [Работа без интернета в момент обмена](offline-at-the-counter.md) калькулятор должен целиком работать без сети с ручным вводом курса, а для этого нужен service worker, который браузеры регистрируют только по HTTPS. По IP без сертификата офлайн-режим невозможен в принципе.

Решение: **бесплатный DDNS-поддомен** (DuckDNS или аналог) + автоматический сертификат Let's Encrypt через Caddy. Стоит ноль, заводится за минуты. ~~Переживает смену ephemeral-IP при перезапуске инстанса~~ — посылка снята в [Открыть 80 и 443](open-web-ports.md): у OCI ephemeral-адрес переживает перезагрузку. См. Resolution. Покупать домен ради калькулятора смысла нет.

### Что осталось

Только подтвердить, что машина вообще принимает входящие снаружи — вынесено в task-ticket [Открыть 80 и 443 и подтвердить внешнюю доступность](open-web-ports.md). До его закрытия выбор Oracle остаётся гипотезой: без портов нет ни HTTPS, ни офлайн-режима, и тогда запасной вариант — GitHub Pages.

## Что уже установлено

- Полный список runtime-возможностей, доступных Artifact на аккаунте пользователя: `artifact`, `db`, `downloads`, `mcp`, `room`, `sample`, `self`. **Сетевого доступа не даёт ни одна.** Установлено по документации платформы и списку возможностей, не экспериментом.
- Репозиторий пользователем разрешён явно; готов поставить любой MCP или skill; есть бесплатный Oracle Cloud (2026-09-03).
- GitHub Pages и Artifact как альтернативы отброшены решением пользователя в пользу Oracle. GitHub Pages остаётся запасным вариантом, если Oracle окажется непригоден (например, из-за освобождения инстанса).

## Resolution (2026-09-04)

**Приложение живёт на Oracle Cloud как статика: cron пишет `rates.json`, Caddy раздаёт папку `site/` по HTTPS на имени DuckDNS. Код едет через публичный GitHub-репозиторий `transfer-calc` по шаблону `reels-tg-bot`.**

Блокер закрыт, машина отвечает снаружи — Oracle перестал быть гипотезой, и все четыре развилки этого тикета решены.

### Форма развёртывания — «cron + статика», подтверждена

Долгоживущего backend нет. Планировщик — **cron, а не systemd-timer**: на этой машине периодический скрипт уже заведён через `crontab` (обновление `yt-dlp` у бота), и второй механизм ради одного файла не окупается.

Бонус, которого не было в исходной рекомендации: `rates.json` лежит **на том же origin**, что и страница, поэтому CORS в раздаче не участвует вообще — ни для НБМ, ни для Прибанка.

Отклонено:

- **живой backend** (FastAPI/uvicorn) — ~60–80 МБ резидентно навсегда при 445 Mi свободных и 352 Mi уже в swap, рядом с пиками `ffmpeg` у бота. Свежесть, которую он даёт, на курсах, меняющихся раз в несколько дней, неотличима от снимка;
- **GitHub Actions вместо Oracle** — расписания best-effort с задержками, workflow отключается сам после 60 дней без активности в репозитории, плюс коммит `rates.json` каждые полчаса. Oracle к этому моменту уже оплачен работой по открытию портов.

Частота cron здесь не фиксируется — она зависит от состава источников, а это следующий тикет.

### Веб-сервер — Caddy

Память играет **против** этого выбора: nginx в простое ~5–10 МБ, Caddy ~25–40 МБ. Выбран всё равно: Caddy сам получает и продлевает сертификат Let's Encrypt и сам редиректит `http → https`, конфиг под задачу — три строки. У nginx это отдельный certbot со своим таймером продления. 20–30 МБ на фоне `ffmpeg`, выдавливающего страницы гигабайтами, — не та экономия, ради которой стоит брать на себя ручное продление.

**Корень раздачи — `site/`, а не корень репозитория.** Следствие важное: `Docs/`, `.git` и `SERVER.md` физически недоступны снаружи даже при публичном репозитории. Деплой ровно как у бота: `git pull --ff-only` в корне, Caddy смотрит в подпапку.

### Имя для HTTPS — DuckDNS

Решающий факт, проверенный 2026-09-04 по [Public Suffix List](https://publicsuffix.org/list/public_suffix_list.dat): `duckdns.org` и `dynv6.net` в списке есть, **`sslip.io` и `nip.io` — нет**. Значит у бесподписочных вариантов все поддомены во всём мире делят один лимит Let's Encrypt в 50 сертификатов в неделю — известный способ получить отказ выпуска не по своей вине. У DuckDNS лимит свой на каждое имя.

Второй довод, не менее весомый: имя вида `<ip>.sslip.io` кодирует адрес, поэтому смена IP меняет **origin**. К origin привязаны и кеш service worker, и ярлык на домашнем экране — сменился origin, и установленное приложение стало другим приложением с пустым кешем. Ровно в тот момент, когда что-то пошло не так.

dynv6 технически не хуже; DuckDNS выбран за простоту — логин через GitHub, токен, одна строка в cron.

### Код — публичный репозиторий `transfer-calc`

Шаблон бота повторяется целиком: GitHub → clone в `/home/ubuntu/transfer-calc` → `git pull --ff-only` через `deploy/redeploy.sh`. Публичность выбрана пользователем: проект не монетизируется, а разбор решений имеет ценность для резюме.

**Публичность потребовала работы, которой не предполагалось.** `open-web-ports.md` содержал OCID инстанса, публичный и приватный IP, имена VCN и имя самой машины — то есть готовую инвентаризацию коробки, которую только что открыли в интернет. git-история необратима, поэтому вычищено **до первого коммита**, а не после:

- реальные значения вынесены в **`SERVER.md`**, он в `.gitignore`; тикеты ссылаются на него вместо значений;
- из метаданных `Калькулятор перевода.xlsx` убрано настоящее имя в `lastModifiedBy` (аккаунт на GitHub псевдонимный, почта noreply). Файл после правки проверен документированным способом — Excel COM, `CalculateFullRebuild()`: **0 ячеек с ошибкой**, 86 shared strings и оба листа как были;
- в репозиторий добавлены `README.md`, `.gitignore` и заглушка `site/index.html` — последняя нужна, чтобы проверить HTTPS до того, как написан калькулятор.

**Конвенция для будущих сессий:** идентификаторы машины в тикеты не писать — писать в `SERVER.md`.

**Проверка перед публикацией (2026-09-05).** Все 18 файлов коммита разобраны по содержимому, xlsx — по каждой части архива: ни почт, ни телефонов, ни токенов, ни ключей, ни номеров карт, ни фамилии. Из IPv4 встречаются только `0.0.0.0` в правилах фаервола и `169.254.169.254` — фиксированный metadata-адрес, одинаковый на всех инстансах OCI. Коммиты идут под `noreply`-почтой GitHub, настоящая не светится.

Утверждение первой редакции этого раздела, будто в `CLAUDE.md` остаётся путь с именем пользователя, **оказалось неверным** — такого пути там нет. Имя встречалось ровно дважды, оба раза в самих тикетах, и убрано.

### Что не решается здесь

- **Состав источников и частота cron** → [Что тянет браузер сам, а что через сервер](browser-or-server-fetch.md).
- **Фактический выпуск сертификата** → [Выпустить сертификат: DuckDNS, Caddy, HTTPS](issue-tls-certificate.md). Порты доказали проходимость TCP, но **не** успех ACME: HTTP-01 может упереться в распространение DNS, лимиты или конфиг. Пока сертификат не выписан, HTTPS остаётся непроверенной посылкой ровно так же, как до предыдущего тикета была непроверенной проходимость портов — а без HTTPS нет service worker и офлайн-режима в кассе.
