# Открыть 80 и 443 и подтвердить внешнюю доступность

## Что надо сделать

Решать здесь нечего — это работа, без которой нельзя закрыть [Где живёт приложение](where-the-app-lives.md). Пока не подтверждено, что машина принимает входящие на 80 и 443 снаружи, выбор Oracle остаётся гипотезой: без этих портов нет ни HTTPS, ни Let's Encrypt, ни service worker, а без service worker не работает офлайн-калькулятор в кассе.

Снято с машины 2026-09-03: слушают только 22, 53 (локальный resolver) и 111 (rpcbind). Веб-сервера нет. `iptables` пропускает из нового только 22 и заканчивается на `-A INPUT -j REJECT`. Значит закрыты **оба** уровня: облачный Security List (почти наверняка) и локальный iptables (точно).

## Чек-лист

### 1. Облачный фаервол — Security List в OCI

Пользователь не нашёл этот раздел. Надёжный путь — от самого инстанса, а не через меню Networking:

1. **Compute → Instances → нужный инстанс**.
2. Пролистать вниз до блока **Primary VNIC**.
3. Кликнуть по имени **Subnet** — это ссылка.
4. На странице подсети, в разделе **Resources** слева, выбрать **Security Lists**.
5. Открыть **Default Security List for …** → вкладка **Ingress Rules**.
6. Если правил для 80 и 443 нет — **Add Ingress Rules**, по одному на порт:
   - Source Type: `CIDR`, Source CIDR: `0.0.0.0/0`
   - IP Protocol: `TCP`, Destination Port Range: `80`, затем то же для `443`.

### 2. Локальный фаервол — iptables

Правила обязаны попасть **выше** финального REJECT. Номер позиции подставлять не нужно — вставка без номера кладёт правило первым, то есть заведомо раньше REJECT:

```
sudo iptables -I INPUT -p tcp -m state --state NEW --dport 80 -j ACCEPT
sudo iptables -I INPUT -p tcp -m state --state NEW --dport 443 -j ACCEPT
sudo iptables -S INPUT
```

Правила должны пережить перезагрузку:

```
sudo apt install -y iptables-persistent
sudo netfilter-persistent save
```

### 3. Проверка снаружи

Слушатель поднимать **из пустого каталога**: `http.server` раздаёт наружу всё, что лежит в текущей директории, а в `/home/ubuntu` лежит `reels-tg-bot` с токеном бота.

```
mkdir -p /tmp/porttest && cd /tmp/porttest && echo ok > index.html
sudo python3 -m http.server 80
```

С домашнего компьютера: `curl -sS -m 10 http://<IP сервера>/` — должен вернуть `ok`. Затем Ctrl+C и то же самое для 443, который и нужен на самом деле:

```
sudo python3 -m http.server 443
```

Проверка: `curl -sS -m 10 http://<IP сервера>:443/` — тоже `ok` (обычный http на 443-м порту; сертификата тут ещё нет, проверяется проходимость порта, а не TLS). После проверки остановить слушатель.

Если не отвечает — почти всегда забыт первый пункт. Классическая ошибка на Oracle: два независимых фаервола, локальный открыли, облачный нет.

### 4. Заодно уточнить в консоли

- **Публичный IP — ephemeral или reserved?** Надёжный путь — Networking → **IP management** → **Reserved public IPs**: если адреса в списке нет, он ephemeral. ~~Ephemeral меняется при stop/start~~ — **посылка неверная**, это поведение AWS. См. Resolution.
- **Тип аккаунта.** Профиль справа вверху → имя tenancy, либо **Governance & Administration → Account Management → Upgrade and Manage Payment**. Если видна кнопка «Upgrade to Paid» — аккаунт всё ещё Free Tier. Влияет на политику освобождения простаивающих инстансов.

## Resolution (2026-09-04)

**Порты открыты, машина отвечает снаружи. Oracle перестал быть гипотезой — выбор подтверждён.**

### Оба фаервола были закрыты, и это доказано, а не предположено

Диагностика шла по типу отказа, а не по факту отказа. С домашней машины, до любых изменений: порт 22 — TCP-хендшейк за 220 мс; порты 80 и 443 — **таймаут** `curl: (28)` на 8 с. Локальное правило `-j REJECT --reject-with icmp-host-prohibited` вернуло бы ICMP, и curl отчитался бы мгновенно; молчаливый дроп означал, что пакеты до хоста не доходят. Значит резал облачный уровень — при том что локальный тоже был закрыт.

Это дало бесплатный способ развести два уровня. После открытия iptables, но **до** правки Security List, замер повторён: снова таймаут. Слушателя не было, поэтому при открытом Security List ядро прислало бы RST и curl сказал бы «connection refused» мгновенно. Таймаут ⇒ облачный уровень всё ещё закрыт. После правки Security List тот же замер без слушателя дал `curl: (7)` за 2,2 с — то есть RST от ядра, пакеты дошли. Каждый уровень подтверждён отдельно.

### Что сделано на машине

- Правила `ACCEPT` для 80 и 443 вставлены позициями 5 и 6, ровно над финальным REJECT.
- Сохранены через `netfilter-persistent save`; `iptables-persistent` был уже установлен, `/etc/iptables/rules.v4` существовал с мая.
- Перед сохранением сделан бэкап `/etc/iptables/rules.v4.bak-preweb` и `rules.v6.bak-preweb`. Diff после сохранения показал **только две новые строки**; остальное — косметика (шапка Oracle заменена на шапку iptables-save, счётчики пакетов, `--dport 123` получил явный `-m udp`). Цепочка Oracle `InstanceServices` с доступом к 169.254.169.254 не пострадала — это важно, через неё идут metadata и NTP.
- `systemctl is-enabled netfilter-persistent` → `enabled`, в сохранённом файле обе строки на месте. Правила переживут перезагрузку.

### Что сделано в консоли (пользователем)

Два ingress-правила `0.0.0.0/0` / TCP / 80 и 443, stateful, в Default Security List.

Отдельная ловушка, стоившая времени: **в тенанси две VCN с одинаковым именем и одинаковым CIDR**, созданные с разницей в 27 секунд 30.06.2026. По списку в консоли они неразличимы. Нужная определена не угадыванием, а с самой машины: `search` в `/etc/resolv.conf` совпал с колонкой DNS Domain Name у верхней строки. Вторая VCN — пустой дубль. Если придётся возвращаться в сетевые настройки, различать только по DNS Domain Name.

Путь «Primary VNIC» из чек-листа в текущей консоли не сработал — блок не находится поиском по странице. Рабочий путь оказался в обход инстанса: Networking → VCN → Subnets → Security Lists.

### Проверка снаружи

Временный `python3 -m http.server` из пустого `/tmp/porttest` с файлом `index.html` = `ok`:

| Порт | Результат с домашней машины |
|---|---|
| 80 | `HTTP 200`, тело `ok`, **102 мс** |
| 443 | `HTTP 200`, тело `ok`, **89 мс** |

443 проверялся обычным http на этом порту — здесь проверяется проходимость порта, а не TLS; сертификата ещё нет.

После проверки слушатель снят, `/tmp/porttest` удалён, состояние машины вернулось к исходному: слушают только 22, 53 (локально) и 111.

### Факты об инстансе

Конкретные идентификаторы (OCID, IP, имена VCN, имя инстанса) вынесены в `SERVER.md`, который не входит в публичный репозиторий.

| | |
|---|---|
| Instance OCID | в `SERVER.md` (вне репозитория) |
| Имя | в `SERVER.md` |
| Регион | `eu-frankfurt-1`, AD-3 |
| Compartment | совпадает с tenancy ⇒ корневой |
| Приватный IP, подсеть, VCN | в `SERVER.md` |
| Публичный IP | в `SERVER.md` — подтверждён исходящим запросом с самой машины |
| Тип IP | **ephemeral** — Reserved public IPs в корневом compartment пуст |
| Тип аккаунта | **Free Tier** — кнопка «Upgrade to Paid» видна |
| `oci` CLI | не установлен ⇒ Security List из-под машины не читается |
| SSH | алиас и доступ — в `SERVER.md`; пользователь `ubuntu`, sudo без пароля |

Мелочь на будущее: ssh из Git Bash на этой Windows-машине не читает `~/.ssh/config` из-за кириллицы в пути к профилю. Рабочий бинарник — `/c/Windows/System32/OpenSSH/ssh.exe`.

### Ephemeral — но не в том смысле, в каком предполагал чек-лист

Страница **Reserved public IPs** в корневом compartment пуста («No items to display»), а инстанс именно там — следовательно публичный адрес инстанса **ephemeral**.

При этом посылка чек-листа «ephemeral меняется при stop/start» **не подтвердилась**. Это поведение AWS EC2, у OCI модель другая. По [документации Oracle](https://docs.oracle.com/en-us/iaas/Content/Network/Tasks/managingpublicIPs.htm) ephemeral-адрес остаётся за инстансом при остановке и перезагрузке и удаляется только когда инстанс **терминирован**, либо отцеплен VNIC, либо удалён приватный IP.

Последствие для проекта — риск меньше, чем ожидалось: рутинный рестарт машины TLS не ломает. Адрес теряется только если инстанс уничтожить и создать заново — что на Free Tier реально ровно в одном сценарии: освобождение простаивающего Always Free инстанса.

Главное: **на решение про DDNS это ничего не меняет**. DDNS нужен не ради смены IP, а ради **имени**: Let's Encrypt не выписывает сертификат на голый IP, а без HTTPS нет service worker и офлайн-режима в кассе. Отслеживание смены адреса становится вторичным бонусом, а не причиной.

### Замечено попутно, вне этого тикета

- `rpcbind` слушает `0.0.0.0:111`. Снаружи закрыт финальным REJECT, так что прямо сейчас не опасен, но на машине, которую только что открыли в интернет, он не нужен ни для чего.
- Аккаунт Free Tier ⇒ действует политика освобождения простаивающих Always Free инстансов. Планируемый cron раз в 15–30 минут плюс веб-сервер добавляют сетевой активности, что скорее снижает риск, чем повышает.

## Что записать при закрытии

Открылись ли порты, отвечает ли машина снаружи, ephemeral или reserved IP, тип аккаунта. Этого достаточно, чтобы закрыть [Где живёт приложение](where-the-app-lives.md).
